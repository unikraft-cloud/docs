**Live migration** moves an instance from one node to another.
A running instance keeps running while it moves, so it keeps its memory and its state.

Use it to:

- Empty a node before maintenance.
- Move load from a busy node to a quieter one.

## How it works

A migration copies an instance from a source node to a destination node:

- A running instance moves while it runs, and resumes on the destination with its memory and state.
- A stopped instance moves without a snapshot, and an instance in `standby` moves with its snapshot, so it keeps its state.
- The volumes of the instance move with it.
  For a running instance, the platform copies them while the instance runs, and then sends only the blocks that changed.

On the destination, the instance keeps its UUID, name, configuration, and creation time.
Its uptime, start counts, CPU time, and memory-time continue from their values on the source.
Its volumes and its [service group](/platform/services) move with it, and keep their UUIDs and names.

The instance gets new network interfaces on the destination.
Their private IP addresses and MAC addresses come from that node, so look the instance up through its [private FQDN](/platform/networking#internal-communication) rather than keeping its old private IP address.

Once the migration completes, the instance exists only on the destination.
If a migration fails, or you abort it, the instance stays on the source node and resumes there.

## Requirements

- Your account needs the `migration` permission on both nodes.
  Root users have it.
  Your operator grants it to other users, and should grant it only to trusted ones, because the destination creates the instance with the owner and configuration that the source sends.
- The owner of the instance has to exist on the destination node, and the instance counts against the owner's quota there, as a new instance would.
- The names of the instance, of its volumes, and of its service group have to be free on the destination.
- Both nodes need a platform release with live migration, and your operator has to set up the destination to receive migrations.

## Migrating an instance

A migration takes two requests: one to the destination node, which issues a token, and one to the source node, which sends the instance.

There's no dedicated `unikraft` CLI subcommand yet, so the examples use the [`unikraft api`](/cli/unikraft/api) command.
In them, `node-a` and `node-b` are metros of a custom [profile](/tutorials/kraftkit-to-unikraft#profile-management) that point at the API endpoints of the source and destination nodes.

### Issuing a token on the destination

Ask the destination node for a token for the instance:

<CodeTabs syncKey="cli">
```bash title="unikraft"
unikraft api /v1/instances/migrate/accept -X PUT --metro node-b \
  '{"uuid": "<instance-uuid>"}'
```
</CodeTabs>

```json title="Response"
{
  "status": "success",
  "data": {
    "instances": [
      {
        "status": "success",
        "uuid": "<instance-uuid>",
        "url": "ukpmig://api.node-b.example.com:45235",
        "token": "<token>",
        "ttl_s": 300
      }
    ]
  }
}
```

The response holds the migration address of the destination in `url`, and the token.
A token admits one migration, and only of the instance whose UUID you passed.
Leave out `uuid`, or send the request without a body, to get a token that admits any one instance.

A token stays valid for `ttl_s` seconds until its first use.
Set `ttl_s` in the request to choose a lifetime of up to `3600` seconds.
Without it, the node's default applies, which is `300` seconds unless your operator changed it.
Treat the token as a secret, since it lets the holder create an instance on the destination.

### Sending the instance from the source

Pass the `url` and the `token` to the source node:

<CodeTabs syncKey="cli">
```bash title="unikraft"
unikraft api /v1/instances/migrate -X PUT --metro node-a \
  '{
    "uuid": "<instance-uuid>",
    "destination": {
      "url": "ukpmig://api.node-b.example.com:45235",
      "token": "<token>"
    }
  }'
```
</CodeTabs>

You can name the instance by `name` instead of `uuid`, or use `/v1/instances/<instance-uuid>/migrate`.
To move more than one instance, send an array of such objects, each with a token of its own.

The request returns as soon as the platform accepts the migration, with the [`migration` object](#following-a-migration) of the instance.
The source contacts the destination only when the migration starts, so a wrong or expired token doesn't fail the request.
To wait for the outcome instead, set `timeout_s`.
It takes up to the API timeout of the node, which is `60` seconds by default, and `-1` waits for that maximum.
When the timeout expires first, the request reports `Operation timed out` with the `migration` object, and the migration goes on.
Without `timeout_s`, a failed migration reports no error: the `migration` object disappears, and the instance stays on the source.

## Following a migration

While an instance migrates, its status on the source node has a `migration` object:

```json
"migration": {
  "destination": "ukpmig://api.node-b.example.com:45235",
  "state": "copying",
  "total_bytes": 1073741824,
  "copied_bytes": 268435456
}
```

| Field | Meaning |
|---|---|
| `destination` | The migration address of the destination node. |
| `state` | The phase of the migration. |
| `total_bytes` | The size of the files that the migration copies, such as volumes and the snapshot, once the platform knows it. |
| `copied_bytes` | How much of `total_bytes` the platform has copied so far. |

The `state` takes these values:

| State | Meaning |
|---|---|
| `waiting` | The migration waits for the instance to finish starting, stopping, or suspending. |
| `queued` | The migration waits for a free slot, since a node copies the files of at most four migrations at the same time. |
| `copying` | The platform copies the configuration and the files of the instance. |
| `syncing` | The platform transfers the running instance. |
| `committing` | The source hands the instance over to the destination. |
| `aborting` | The platform rolls the migration back. |

Read it with `unikraft api /v1/instances/<instance-uuid> --metro node-a`.
Only accounts with the `migration` permission see the `migration` object.
During the migration, the destination lists its copy of the instance, with `"incoming": true` in place of `destination`.
When the migration completes, the instance disappears from the source node.

Queued migrations start in the order of their requests.
While a migration waits, you can still start, stop, and change the instance.
The platform checks the instance again when the migration starts, and fails the migration if the instance no longer qualifies.
If the instance is only busy at that point, the migration keeps its place in the queue and tries again later.

While the instance migrates, the platform refuses changes to it, to its service group, and to its volumes.
It also refuses to suspend the instance, and to stop it without `force`.
A forced stop or a delete of the instance aborts the migration, until the migration reaches `committing`.
A stopped instance can still start until the destination has a complete copy, and the migration then moves it as a running instance.

A restart of the platform controller doesn't cancel a migration.
The migration picks up where it stopped.

## Aborting a migration

Abort a migration on the source node:

<CodeTabs syncKey="cli">
```bash title="unikraft"
unikraft api /v1/instances/migrate/abort -X PUT --metro node-a \
  '{"uuid": "<instance-uuid>"}'
```
</CodeTabs>

You can also use `/v1/instances/<instance-uuid>/migrate/abort`.
The request returns at once, and the platform rolls the migration back in the background.
The instance stays on the source node and resumes there.
You can abort a migration in every state before `committing`.

## Error handling

| Error message | Cause |
|---------------|-------|
| `Failed to migrate instances: insufficient permissions` | Your account lacks the `migration` permission on the node, which reports `Failed to accept migrations` or `Failed to abort migrations` for the other requests. |
| `Failed to accept migration: this node accepts no migrations` | The destination node isn't set up to receive migrations. |
| `Failed to accept migration: too many migrations accepted` | The destination holds too many tokens, so wait until migrations use them or they expire. |
| `Failed to accept migration: too many unused tokens of this user` | You hold 1024 unused tokens on the destination, so use them or wait for them to expire. |
| `The destination URL is invalid` | The `url` is empty or too long. |
| `The destination token is invalid` | The `token` doesn't have the format of a token. |
| `Failed to start migration: EOPNOTSUPP` | The instance, or one of its volumes, can't migrate yet (see [Limitations](#limitations)). |
| `Failed to start migration: EBUSY` | The instance or one of its volumes is busy, for example with a snapshot, a scheduled restart, a volume operation, a template that isn't ready, or another migration, so retry later. |
| `Failed to start migration: EIO` | A volume of the instance is in the error state. |
| `Failed to start migration: service group changed, retry` | The service group of the instance changed during the request, so send it again. |
| `Failed to migrate: migration aborted` | An abort request, a forced stop, or a delete ended the migration while the request waited for it. |
| `Failed to migrate: <error>` | The migration failed after it started, for example because the destination refused the token, and the instance stays on the source. |
| `Failed to update instance: the instance is migrating` | You changed an instance during its migration, so wait until the migration ends, and its service group and volumes report similar messages. |
| `Failed to abort migration: the instance is not migrating out` | The instance has no migration to abort on this node. |
| `Failed to abort migration: the migration can no longer be aborted` | The source already committed the instance to the destination. |

## Limitations

The platform doesn't migrate the following instances yet:

- Instances created with `"type": "full"` (full VMs, see [instance types](/platform/instances#instance-types)).
- Instances with [vertical scaling](/features/vertical-scaling).
- Instances of [kernel-less images](/platform/images#platform-kernel).
- Instances with [inline ROMs](/features/roms#inline-roms).
- [Templates](/platform/instances#instance-templates), and instances that are becoming one.
- [Autoscale](/features/autoscale) instances, and instances in a service group with autoscale.
- Instances with [autokill](/features/autokill), and instances that the platform deletes when they stop.
- Instances with dependencies, and instances that running instances depend on.
- Instances with changes to volumes, ROMs, or dependencies that wait for the next restart.
- Instances in a service group with custom certificates, or in a [persistent service group](/platform/services#persistent-service-groups).
- Instances with a [custom TAP device](/features/custom-network-configuration), a [relay](/features/network-shield), or `autoconfig` turned off on an interface.
- Instances with network interfaces on a node in [managed network mode](/features/custom-network-configuration#managed-network-mode), since each of those interfaces uses a custom TAP device.

Instances cloned from a template can migrate once their template is ready.

Every volume of the instance has to qualify, or the instance doesn't migrate.
A volume qualifies when it has the same owner as the instance, no other instance has it attached, and it's neither a [managed volume](/features/managed-volumes) nor a [`virtiofs` volume](/platform/volumes#filesystems).
